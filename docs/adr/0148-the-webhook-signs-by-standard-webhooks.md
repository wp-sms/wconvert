# 0148: The webhook signs by Standard Webhooks

Date: 2026-10-13. Status: accepted.
Amends [0007](0007-destinations-are-outbound-and-fallible.md),
[0008](0008-delivery-state-is-destination-health-not-per-lead.md),
[0049](0049-the-mailpoet-push-adds-membership-without-touching-status.md),
[0074](0074-destinations-declare-requirements-and-show-shared-usage.md) and
[0110](0110-integrations-share-setup-and-map-extra-answers-per-campaign.md).
Delivers the generic webhook #35 promised.

Until now the only outbound pushes were Pro's Mailchimp, Brevo and Mailtrap
adapters. The HMAC code in the repo signed capture grants, not outgoing data.
This ADR adds **one Pro [[Destination]] type, `webhook`**: a signed JSON POST
of each accepted submission to a URL the merchant pastes.

No popup or form plugin we surveyed signs with a timestamp. OptinMonster sends
no authentication. Gravity Forms, WPForms, Fluent Forms and Elementor are
unsigned or vague. Typeform and Tally sign without a timestamp, so a captured
request replays forever. The receivers merchants actually use (Zapier, Make,
n8n, Pabbly) verify no signature at all; they rely on a secret URL or an
API-key header. So there are two layers: custom headers for no-code tools, and
Standard Webhooks signing for developers.

## Decisions

**1. Signing is [Standard Webhooks](https://www.standardwebhooks.com/), and
nothing of ours.** Each attempt carries:

- `webhook-id` — `msg_` and 32 hex characters of
  `sha256(lead id | submission id | destination id)`. The same on every retry,
  different per submission and per route. It is the receiver's dedupe key.
- `webhook-timestamp` — Unix seconds, fresh on every attempt.
- `webhook-signature` — `v1,` and base64 HMAC-SHA256 over
  `{id}.{timestamp}.{body}`, keyed by the secret's decoded bytes.

The secret is `whsec_` and 32 random bytes, base64, **generated by the server**
and never accepted from the browser. The body is encoded once, and the signature
covers those exact bytes, so emoji and non-Latin answers verify.
`WebhookSignature` is tested against the specification's own vector. Receivers
verify with the `standardwebhooks` libraries in three lines.

**2. The URL is a credential.** A Zapier catch hook or a Make webhook
authenticates by being secret. So the URL lives on the [[Connection]], which
REST never returns (`Connection::masked()`), and not in Destination settings,
which it does. The Connection holds `url`, `signing_secret`, up to five
`headers` and `setup_site_url`. `accountIdentity` is the URL's host. Queued
jobs re-read the Connection, and `RouteIdentity` hashes the connection id, not
its credentials, so a corrected URL takes effect for leads already queued.

The generic part is in Free's controller as three connection field kinds:
`secret` (generated, returned once in `revealed`, regenerated by
`POST /connections/{id}/regenerate`), `site_url` (recorded on first save) and
`headers` (name/value pairs; names are HTTP tokens, values have no line breaks,
and a field's `reserved` names are refused on save). `masked()` reports a
header list by its names, never its values. A type may throw
`ConnectionRefused` to show the merchant its own sentence on save.

**3. Regenerating switches at once.** There is no overlap window. The next
attempt signs with the new secret, and a receiver still on the old one refuses
it, which needs attention until the merchant pastes the new one in.

**4. Custom headers may not frame the request.** `webhook-*`, `Content-Type`,
`Content-Length`, `Host`, `User-Agent`, `X-WConvert-Event`,
`Transfer-Encoding` and `Connection` are refused on save and dropped at send.
Every request also sends `Content-Type: application/json`,
`User-Agent: WConvert/{version}` and `X-WConvert-Event: lead.captured`.

**5. Payload v1 is one documented shape.** There is no body template or field
mapping (`settingsSchema()` is empty), and it is JSON only.

```json
{"id":"msg_…","type":"lead.captured","version":1,"timestamp":"2026-10-13T09:12:44Z","test":false,
 "site":{"url":"https://shop.com","environment":"production"},
 "data":{"lead_id":"01J…","submission":"primary",
   "contact":{"email":"…","phone":null,"name":"…"},
   "interest":null,
   "answers":{"budget":{"question":"Budget?","answer":"1k–5k"}},
   "campaign":{"id":"…","name":"Spring sale popup","goal":"grow_email_list"},
   "source":{"page_url":"/pricing","utm":{"source":"fb","medium":null,"campaign":null,"term":null,"content":null}},
   "consent":{"purpose":"email_marketing","email":{"text":"…","accepted_at":"…"},"sms":null}}}
```

- **Every key is always present**, null where empty, because Zapier and Make
  learn a webhook's fields from the first payload. `answers` is always an
  object. A multi-choice answer is a list of labels; the others are a string.
- `contact.name` is the one name field the capture vocabulary has. It is not
  split into first and last, for the same reason the Mailtrap push sends it
  whole.
- `id` repeats `webhook-id`, because a no-code receiver cannot easily read
  headers.
- Body `timestamp` is when the submission was **accepted**. The header
  timestamp is when it was **sent**, so a retry a day later still passes a
  receiver's five-minute window.
- **One POST per accepted submission, each a full snapshot of the journey up
  to that submission** — never past it. A two-step email→SMS signup
  (ADR 0103) posts twice with one `lead_id`, and the second carries both. A
  retry of the first after the second step still describes the first.
  `PushDetails` builds this from the Lead's accepted snapshots.
- No IP address and no user agent.
- `site.environment` is `wp_get_environment_type()`. A staging copy is tagged
  and warned about, never blocked: the controller reports `environment` and
  each Connection's `site_changed` (its `setup_site_url` is not this site).
- `PushSubject` gains `deliveryId` and `details`; `PushContext` gains the
  Optin id and goal. Other types ignore them. A type that forwards the
  submission whole implements the marker `ForwardsWholeSubmission`; only such a
  type receives a campaign editor's questions and campaign on a test, so the
  WSMS push never writes a test's campaign name as `source_ref`. A test send carries a full
  sample with `test: true`. From the campaign editor, the draft test carries
  that campaign's question ids and labels with the merchant's sample answers
  and its campaign, so a receiver can map them before the first real Lead.

**6. The page a Lead came from is recorded on the Lead.** The loader sends
`page_url` (path and query) with the capture request. `CaptureSource` keeps
the path and the five `utm_*` tags and drops every other parameter, because
an `?email=` or a token in a link must not be stored. It filters on the server
because the request is the visitor's to forge, and because filtering in the
loader cost bytes the free loader does not have. It is stored as
`capture.source` in the existing Lead JSON, set by the first submission, and
erased with the Lead. `LeadCsv` gains `page_url` and `utm_*` columns. No table
or column changed.

**7. Retries take about a day.** A type may implement
`DeclaresRetrySchedule::retryDelays()`. The webhook waits +1m, +5m, +30m,
+2h, +6h and +24h: seven attempts, then it needs attention and the manual
resend takes over (ADR 0071). The ESPs keep five doubling attempts. It is still
Action Scheduler, and jobs still carry ids only.

**8. Where a webhook may point.** `WebhookUrlGuard` allows `http` and `https`
on any port, resolves the host, and refuses it if **any** address is loopback,
private, link-local or reserved — PHP's two range flags plus carrier-grade NAT
(`100.64.0.0/10`), benchmarking (`198.18.0.0/15`) and NAT64 (`64:ff9b::/96`,
checked by the IPv4 address it embeds), which those flags let through. `wp_safe_remote_post()` would refuse a
self-hosted n8n on :5678, so the check is ours. It runs on save and again on
every send, to narrow DNS rebinding. Redirects are never followed
(`redirection => 0`), the timeout is 10 seconds, and `sslverify` stays on with
no toggle. A developer may allow their own network with the filter
`wconvert_webhook_allows_private_hosts` (default false).

**9. The receiver's status decides the outcome, and its body is never read.**

| Response | Outcome |
| --- | --- |
| 2xx | success |
| 3xx | attention: paste the address it redirects to |
| 401, 403 | attention: key, headers or firewall |
| 404, 410 | attention: the Zap or scenario is off or deleted |
| invalid TLS certificate | attention |
| 408, 429, 5xx, DNS failure, timeout | retryable |
| other 4xx | terminal |

**10. `testConnection` sends nothing.** It checks the URL guard and the secret
format. A test POST to a Zap would become its first sample and push out the
merchant's real one. *Send a test* is the explicit way to send.

**11. Pro only.** The type registers from Pro's destinations module, and
`tiers.json` names it so free's Destinations hint can (ADR 0147). Free's ZIP
carries no webhook class. `throughput()` is 60, which paces bulk re-push, where
each lead may cost the merchant a Zapier or Make task.

**12. Setup screens: pick the tool, then a form made for it.** Approved on the
prototype (claude.ai/artifact/KJWnB3Hym1VBiL2MpVbgh4, variant B, 2026-10-13).

- *Step 1* asks "Where should signups go?" as four radio cards: Zapier, Make,
  n8n and Your own code, each with the tool's own logo **in colour** — the
  companies' files, never recoloured (sources in
  `pro/modules/destinations/admin/README.md`). *Step 2* asks only what that
  tool needs: a Catch Hook URL; a URL and an optional API key sent as
  `x-make-apikey`; a URL and optional Header Auth; or a URL and up to five
  headers. Every tool stores the same Connection, so the choice decides the
  words, never the data. An existing account skips the picker.
- *The signing secret* is shown once, read-only, with Copy and a note that
  this is the only time. **Done is never blocked**: a receiver that ignores
  signatures has no use for it. Regenerate asks in the footer, not in a
  second dialog (§9), then shows the new one the same way.
- *An account row* shows a tool's logo when the URL's host is that tool's
  (`hooks.zapier.com`, `make.com` and `*.make.com`, `*.n8n.cloud`), else the
  webhook icon — a self-hosted n8n included. The host comes from the
  Connection's `account_identity`, never the URL.
- *Send a test* keeps the sentence as its headline (ADR 0042) and adds the
  receiver's status and time under it: "Answered 200 in 0.4 s."
  `PushResult::withTransport()` carries them; `TestReport` adds `status` and
  `ms` only when set, so an email service's report is unchanged. From a
  campaign, the test carries that campaign's questions with editable sample
  answers.
- *A staging copy* is a badge on the account row, "On a copy of the site",
  and one line under it saying where it was set up — not a banner (§14).
- **Free names no tool.** The picker, the tailored forms, the logos and the
  host mapping are Pro's (`connectionSetup` slots, registered from Pro's admin
  entry), and `module.json`'s `admin_markers` keep them out of free's bundle.
  Free draws the generic field kinds, the one-time secret, the badge, the
  status line, and copy driven by the type's `forwards_submission` flag. The
  free hint becomes general (ADR 0147, amended).

## Consequences

- **A webhook push is not idempotent**, which is the one exception to
  ADR 0008's premise. A POST cannot be upserted from this side, so dedupe
  moves to the receiver: the same `id` in header and body on every attempt.
  A receiver that processed a request but answered too slowly gets it again
  on retry. The guide tells receivers to respond at once and dedupe on `id`.
- Erasing a Lead is **not** forwarded to the receiver. The data flow is
  one-way (ADR 0007). A queued retry for an erased Lead is skipped, as before.
- Deactivating Pro unregisters the type. Captures still land, and its routes
  count a skip rather than a failure, so those leads are **not** in "Not sent"
  (the failure ring). After reactivation, the Destination's bulk re-push sends
  them, together with any recent leads already delivered, which the receiver
  dedupes by `id`. Verified on Playground. The licence gates updates only
  (ADR 0143), so a lapsed one changes nothing here.
- Changing a webhook URL to a different host is refused as a different
  account (the existing `accountIdentity` rule). The merchant connects it as a
  new account.
